## Context

`JsonFileStore._append` 当前顺序为:

1. 取路径锁;
2. 追加写 JSONL 并 `fsync`;
3. `_read_valid_index(path)` —— 此时文件指纹已变化,校验失败;
4. `_build_index(path)` 全量重建;
5. 写索引。

索引的 `source` 指纹由 `(size, mtime_ns, ctime_ns)` 组成,`validate_index` 要求三者与当前文件完全一致。因此步骤 3 永远返回 `None`,步骤 4 永远执行。

`_apply_index_record`(→ `SessionIndex.apply_record`)本身是正确的增量实现,只是从未被调用。

## Goals / Non-Goals

**Goals:**

- 追加一次记录的成本与历史长度无关(常态为 O(1) 索引更新)。
- 索引仍是可重建缓存,JSONL 仍是唯一真相源。
- 冷启动、索引损坏、并发追加、索引写失败四种既有语义保持不变。

**Non-Goals:**

- 不改变索引文件格式、版本号或字段集合。
- 不引入后台线程或异步索引写入。
- 不优化读取路径(它已命中索引)。
- 不改变 `fsync` 策略。

## Decisions

### 1. 交换"读索引"与"写 JSONL"的顺序

正确顺序:

1. 取路径锁(保持并发串行化);
2. `_read_valid_index(path)` —— 文件仍是上次写完的状态,指纹匹配;
3. 若为 `None`,回源 `_build_index(path)`(冷启动/损坏);
4. `_apply_index_record(index, path, record)` —— 注意此时 **不能** 让它读取新指纹;
5. 追加写 JSONL 并 `fsync`;
6. 用新指纹写索引。

第 4 步的指纹处理是关键:`apply_record` 末尾会写 `index["source"] = fingerprint(path)`。若在第 5 步之前调用,它会写入**旧**指纹(这正是我们想要的,因为随后的写索引会用新指纹覆盖),但为了让语义显式,改为在第 6 步统一刷新指纹,并让 `apply_record` 的 `source_fingerprint` 参数接受"跳过刷新"。

备选方案是给索引加"追加后的预期大小"字段做乐观校验,但那会改索引格式,且仍无法避免并发窗口,因此不采用。

### 2. 陈旧索引仍然安全

若进程在"读索引"与"写 JSONL"之间被杀死,JSONL 已追加但索引仍是旧指纹 → 下次读取校验失败 → 回源重建。**陈旧索引只会导致一次重建,不会返回错误数据**,这是选择该顺序的安全依据。

### 3. 失败语义不变

- 索引写失败:`safe_write` 删除索引文件,JSONL 追加已成功 → 下次读取回源重建。
- `fsync` 失败:抛出,由上层处理,索引不写。
- 并发追加:整个步骤在路径锁内,后到者读到的索引已含前者的记录。

## Risks / Trade-offs

- **[锁内多一次索引读]** → 一次小文件 `read_text` + JSON 解析,远小于一次全量扫描;基准测试会覆盖。
- **[`apply_record` 指纹语义变更]** → 通过显式参数控制,并在测试中断言"追加后索引 `source` 与文件一致"。
- **[冷启动仍全量]** → 保持现状,冷启动只发生一次;测试覆盖冷启动后的第二次追加走增量。
